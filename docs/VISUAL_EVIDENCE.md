# Visual Evidence Standard

## Purpose

Visual evidence makes product progress observable and prevents implementation claims from being based on code volume, static mockups or assumptions.

A screenshot is evidence of one observed state at one point in time. It is not, by itself, proof of correctness, persistence, security, responsiveness or full workflow completion. Pair it with tests and reproducible steps.

## 1. Evidence classes

Use one or more of these classes for each increment:

- **V1 — Runtime screenshot:** captured from the actual running application after the change.
- **V2 — Interaction sequence:** screenshots or a short recording showing the meaningful steps and resulting state.
- **V3 — Responsive evidence:** actual rendered states at relevant viewport sizes.
- **V4 — Data/geometry evidence:** actual map, plan, model, component tree, table or 3D view generated from the implementation.
- **T1 — Automated test evidence:** real test output, linked to the command and environment.
- **A1 — API evidence:** reproducible request/response, status and relevant persisted state.
- **A2 — CLI/process evidence:** actual command output, logs or generated artifact.
- **A3 — Domain review evidence:** source, assumptions, units, calculation trace and qualified review where required.

## 2. Rules for screenshots

A valid runtime screenshot must:
- come from the real application or real rendered output;
- show the relevant feature and its resulting state;
- use a reproducible build and realistic, non-sensitive test data;
- avoid secrets, tokens, personal data and confidential property documents;
- not be manually altered to conceal errors or imply behavior that did not occur;
- include enough context to identify the screen/state.

Do not present any of the following as runtime proof:
- Figma or design mockups;
- generated concept art;
- hand-drawn diagrams;
- static HTML that is not connected to the product;
- fabricated data or manually assembled UI;
- a screenshot from a different branch/build without disclosure.

These materials may be useful design references, but label them **Concept / Reference — not implementation evidence**.

## 3. Evidence folder and manifest

Store evidence at:

```text
docs/evidence/<WORK-ID>/
  README.md
  runtime-01.png
  runtime-02.png
  test-output.txt
  api-response.json
```

Only include files relevant to the increment. Never commit secrets or personal/sensitive data.

The `README.md` manifest must state:
- Work ID and claim being demonstrated;
- commit SHA or branch/build identifier;
- date and environment (OS, browser/device, viewport, app version);
- exact steps/commands to reproduce;
- evidence filename and what it demonstrates;
- known limitations and what the evidence does **not** prove.

## 4. Minimum evidence by work type

| Work type | Minimum proof |
|---|---|
| UI behavior | Runtime screenshot plus interaction proof and automated tests |
| Responsive UI | Runtime screenshots at declared viewport sizes |
| API/backend | Automated tests plus reproducible request/response; UI screenshot only if a real UI exists |
| Database/schema | Migration test, integrity/constraint tests, and actual query/state evidence |
| Geospatial | Real map/geometry output with CRS, scale/context and source data identified |
| 2D/3D/BIM | Actual rendered model/view plus source fixture and reproducible generation steps |
| Calculation/simulation | Input/output trace, units, method/version, test cases and review status; visualization where meaningful |
| Refactor/infrastructure | Before/after behavior or metrics, regression tests and relevant logs; do not invent a visual requirement |

## 5. Evidence quality gate

For every claimed proof, ask:
1. Is this output generated by the current implementation?
2. Can another developer reproduce it?
3. Does it show the exact acceptance criterion?
4. Is the source data identified and safe to publish?
5. Does it hide any failure or uncertainty?
6. Is it paired with tests appropriate to the claim?

If any answer is no, qualify the evidence or capture it again.

## 6. No fake green

- Never fabricate screenshots, test logs, benchmark numbers or API responses.
- Never use a passing screenshot to imply tests passed.
- Never use passing tests to imply the UI works.
- Never mark a missing screenshot as complete because a mockup exists.
- If the environment cannot run the product, record the blocker and provide the strongest available reproducible evidence. Keep the work item Partial or Blocked.
